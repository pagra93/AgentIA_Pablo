## Wiki Disciplina (centro de conocimiento de empresa)

La wiki en `docs/general/wiki/` es la memoria viva del proyecto y de la empresa. Es **transversal a todas las áreas** (Producto, Marketing, RRHH, Operaciones). Mantén el contexto siempre actualizado, **siempre pidiendo confirmación antes de actuar**.

### 1. Detectar source nuevo
Cuando el usuario aporte un artículo, una transcripción, o un copy-paste largo:
- Pregunta: "¿lo guardo en `raw/` y lo ingesto al wiki? ¿Qué tipo (artículo / reunión / nota)?"
- Si sí → guarda en `raw/<tipo>/<slug>.md` y ejecuta `/wiki ingestar`

### 2. Detectar entidad/concepto nuevo
Cuando aparezca por primera vez en conversación una persona, librería, API, herramienta o concepto técnico relevante:
- Pregunta: "¿creo entity page para X?"
- Si sí → ejecuta `/wiki ingestar` sobre la nota relevante o crea directamente la entity

### 3. Capturar reuniones
Cuando el usuario mencione "tuve una reunión con X" o "decidimos en la reunión Y":
- Pregunta: "¿registro la reunión? ¿Asistentes, decisiones, action items?"
- Si sí → ejecuta `/wiki reunion <título>` que crea la plantilla rellenable

### 4. Antes de responder consultas no-triviales
**LEE el wiki primero**: `docs/general/wiki/index.md` → páginas relevantes. Cita las páginas en tu respuesta usando wikilinks `[[entities/x]]`.

### 5. Filtrar buenas respuestas
Si tu respuesta es densa y valiosa, pregunta: "¿la archivo como concept/topic page?"

### 6. Action items de reuniones → tareas PM
Cuando una reunión genera action items, sugiere convertirlos en tareas vía `/pm` (NO ejecutes automáticamente — solo sugiere). Ej: "Esta reunión tiene 3 action items. ¿Los añado al `inbox.md` para que el PM los procese?"

## Coding Disciplina (cuando Claude Code escribe o modifica código)

Estos 4 principios atacan los antipatrones más comunes de coding asistido por LLMs (asunciones silenciosas, sobre-construcción, cambios orthogonales, criterios débiles). Aplica también a los sub-agents de `/build` (ver `rul-llm-coding-discipline`).

### 1. Think Before Coding
- **Enuncia asunciones** antes de codear ("Asumo que X. Si no es así, dímelo.")
- **Si hay ambigüedad**: pregunta. No elijas en silencio.
- **Si hay 2+ enfoques razonables**: presenta tradeoffs y recomienda uno.
- **Si te confundes**: para. Nombra qué no entiendes.
- **Push back honesto**: si Pablo pide algo sub-óptimo, dilo educadamente. No asentir por defecto.

### 2. Simplicity First
- Mínimo código que resuelva. Nada especulativo.
- No abstracciones para código de un solo uso. No "flexibilidad" no pedida.
- No error handling para escenarios imposibles (solo en bordes: input usuario, APIs externas).
- Si 200 líneas pueden ser 50: reescribe. Test del senior: _"¿diría sobre-construido?"_

### 3. Surgical Changes
- Cada línea modificada debe **trazar al request original**.
- No "mejores" código adyacente, comentarios o formato.
- Si ves dead code o deuda técnica orthogonal: **menciónalo en el reporte**, no lo arregles en este commit.
- Match el estilo existente. Limpia solo huérfanos que TUS cambios crearon.
- **Boy Scout Rule**: la cleanup va en commit aparte (Pablo aprueba), no contamina el diff del feature.

### 4. Goal-Driven Execution
- Antes de codear: define cómo se ve "hecho". Si no puedes, pregunta.
- Transforma imperativo vago → criterio testable ("arregla bug" → "test que reproduce el bug, hazlo pasar").
- Multi-step: enuncia plan numerado con verificación por paso.
- Tests-first para lógica pura. Implementation-first para UI.

Ver `~/.claude/skills/rul-llm-coding-discipline/SKILL.md` para ejemplos completos.
